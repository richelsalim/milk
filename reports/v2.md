# v2 running report

One section per phase (IMPLEMENTATION_V2.md). Every number here comes from a run in
this repo; bench rows land in reports/zoo_baselines.md and are transcribed here.

## Phase V2.0: free budget — snapshots, throughput, recency weights

### Profile of one full-data ple epoch (12-core CPU, torch 6 threads)

| section | wall |
|---|---|
| v1 batch assembly + gathers (276 batches, python per-batch concatenate) | 0.23 s |
| v2 batch assembly + gathers (one vectorized permutation per epoch) | 0.14 s |
| one full epoch incl. setup + 1 val predict + eval | 49.6 s |
| val forward pass (124,909 rows) | 1.3 s |
| one metric evaluation (prepare.evaluate on val) | 0.2 s |

Verdict: batch assembly was never the bottleneck — forward/backward dominates at
~45 s/epoch. The waste v1 actually carried was *redundant forward passes after
training*: the multitask head grid re-predicted validation 16x (~21 s) and snapshot
selection re-predicted for its own scoring. Both now run off the per-epoch validation
prediction cache: selection and the head grid cost metric evaluations only (0.2 s
each), zero extra forwards. A fit-time forward pass now happens exactly once per epoch
(unit-tested).

### Throughput target (>= 8 full-data ple epochs in 300 s): missed, measured best documented

One-epoch walls for the prescribed knobs (1 epoch, full data, head grid off):

| config | epoch wall | primary after epoch 1 |
|---|---|---|
| batch 4096, 6 threads (default) | 47.1 s | 0.6030 |
| batch 8192, lr 2e-3, 6 threads | 45.8 s | 0.6020 |
| batch 4096, 8 threads | 47.5 s | 0.6031 |
| batch 8192, lr 2e-3, 8 threads | 44.5 s | 0.6019 |

The epoch is compute-bound in the model's own matmuls (~12 expert/gate/tower MLPs over
1.14M rows); batch 8192 with scaled lr buys ~5% wall and costs quality at equal epoch
count, extra threads buy nothing (6 physical cores). Measured best on this machine is
~45 s/epoch => ~6 early-stopped epochs inside 300 s, unchanged from v1; the recovered
~25 s of post-fit forwards goes to the snapshot ensemble instead, which reuses the same
6 epochs at zero extra cost. Batch stays 4096, lr stays 1e-3. This is a research
target, not an environment gate — continuing per the guide.

### Snapshot ensembling (snapshot_k=3 default for deepfm/dcnv2/mmoe/ple/din_lite)

Top-3 epochs by cached validation primary, state dicts kept for test-time averaging,
ensemble adopted only when it beats the single best epoch (recorded per fit in
info.snapshot_ensemble).

`python -m recsys.zoo bench --budget 300 --models ple,deepfm` (walls <= 330 s: gate ok):

| model | primary | gauc | ndcg5 | wall | v1 primary | delta |
|---|---|---|---|---|---|---|
| ple | **0.6065** | 0.6743 | 0.5387 | 311 s | 0.6062 | +0.0003 |
| deepfm | **0.6066** | 0.6738 | 0.5393 | 125 s | 0.6057 | +0.0009 |

Research target ple >= 0.6065: hit. The bigger surprise is deepfm: with the top-3

sample. The knob stays in the environment (`recency_half_life_days`, default None
everywhere) as a documented dead end.

## Phase V2.1: positive-history attention

seq_pos block: the user's last 20 long_view==1 impressions before the row (video /
author / tag ids, duration, watch ratio), strict-past for train with the same
(user_id, time_ms, _idx) tie order as seq, training-window tail for val/test,
padded -1/0. Spec full_seqpos = full + seq_pos (185 columns). din_lite gained
config history="all"|"positive" selecting the attended block; trunk excludes sp_
like sq_. Time-safety tests (later-label shuffle invariant, earlier-positive flip
seen, negatives never enter) green; full_seqpos no-label/group-order test green.

Bench (budget 300, snapshot_k=3):

| model | primary | gauc | ndcg5 | wall |
|---|---|---|---|---|
| din_pos (history=positive, full_seqpos) | 0.6045 | 0.6718 | 0.5373 | 299 s |
| din_lite v1 row (history=all, full_seq) | 0.6048 | 0.6721 | 0.5376 | 306 s |

Research target (beat 0.6048): missed by 0.0003; nowhere near ple 0.6065, so
din_pos is NOT promoted into the V2.2 candidates and the registry default stays
history="all". Why the statement's "positive history" lead does not pay here: the
~66%-negative stream is informative contrast the attention can already weight
(filtering discards rows without adding information), and in a 14-day window the
last-20-positives tail covers most users' entire positive history anyway, so the
"positive" variant mostly loses sequence resolution. Recorded as a dead end with
the mechanism kept available for the scored run to revisit.

## Phase V2.2: blend v2

Machinery added to Blend (recsys/models/blend.py): optional `weight_grid` — after the
bases fit, each base's validation ranks are computed once and <= 12 weight combos are
scored through prepare.evaluate, best kept (selection cost recorded in info: 4-13 s of
metric evals, same precedent as the multitask head grid); per-base `seed_offset` for
bagging; FMRec gained a `fields` config so a 5-id-field FM can ride the full spec
inside a blend (fm5's own path is untouched).

Candidates, one 300 s budget each (walls <= 330 s, all green; seed 0):

| candidate | bases (share) | primary | wall | grid chose |
|---|---|---|---|---|
| blend3_fdp | fm-ids .12 / deepfm .36 / ple .48 | 0.6071 | 307 s | .10/.35/.55 |
| blend3_fpp | fm-ids .10 / ple .43 / ple(seed+1) .43 | 0.6055 | 317 s | .05/.475/.475 |
| blend3_dpp | deepfm .28 / ple .34 / ple(seed+1) .34 | 0.6059 | 318 s | .35/.35/.30 |
| blend2_dp | deepfm .40 / ple .56 | **0.6075** | 297 s | .45/.55 |
| blend2_dp42 | deepfm .42 / ple .56, finer grid | 0.6075 | 297 s | .45/.55 (same fits) |

Research target (>= 0.6076 = v1 + 0.0005): missed by 0.0001 at 0.6075 (+0.0004 over
v1's 0.6071); stretch 0.6091 out of reach. What the sweep says about the ceiling:
adding a third base never pays — fm-ids brings no diversity the pair lacks (its grid
weight collapses to 0.10 and the result ties v1), and every configuration that splits
ple's budget (fpp, dpp) loses outright because ple's marginal epochs are worth more
than any bagging/diversity gain at this budget. The whole gain over v1 comes from the
snapshot-lifted bases plus the validation weight grid moving deepfm's weight from
0.35 to 0.45 — consistent with deepfm's rise to 0.6066. The registry default is now
the blend2_dp config; v1's fixed-weight pair stays as `blend_v1`.

### Wall-clock nondeterminism found and fixed

Re-benching the identical winning config (same seed) initially returned 0.6060 and
0.6064 vs 0.6075: any base whose fit is cut by the wall-clock deadline mid-epoch
carries machine-speed dependence (how many batches the partial epoch trained), and at
share boundaries a whole epoch can appear/disappear. Fix shipped in the default: pin
per-base epoch caps inside the shares' comfortable reach (deepfm epochs<=6 — patience
actually stops it at 5, ple epochs=3), so every stop is label-driven (patience or cap,
never the deadline). Three runs of the pinned config: 0.607506 / 0.607506 (candidate
+ gate bench, bit-identical grid primary), wall 261/259 s. The deadline remains as a
safety net for slower machines and is documented as such. Epoch-pinned alternative
with ple 4 epochs (blend_p2, 0.6069) confirmed ple's 4th epoch is not worth deepfm's
6th-to-5th trade.

Final V2.2 state: registry `blend` = deepfm(ep<=6, share .45, snapshot) + ple(ep 3,
share .55, snapshot), rank-average, weight grid of 6 on validation (chose .45/.55),
**0.6075 validation primary** (+0.0004 vs v1, target 0.6076 missed by 0.0001 —
non-blocking, analysis above), 259-261 s wall, deterministic. `blend_v1` fallback
kept.
